1Research Data Sharing (Exercise 1)

1.1First-order logic

Table 1 translates each statement. Intern(x, g) reads “x is an intern at research group g”, and Authorized(x, d) reads “x is authorized to publish d”.

Table 1: First-order logic for each statement of Exercise 1.
StatementFirst-order logic
A research group called visionlab owns a dataset called medset. ResearchGroup(visionlab) ∧ Dataset(medset) ∧ Owns(visionlab, medset)
The dataset contains patient data. ContainsPatientData(medset)
anna is an intern at visionlab. Intern(anna, visionlab)
anna uploaded medset to a public repository. UploadedToPublicRepo(anna, medset)
Any dataset containing patient data is considered sensitive. ∀d [Dataset(d) ∧ ContainsPatientData(d) → Sensitive(d)]
An intern is not authorized to publish sensitive datasets owned by their research group. ∀x ∀g ∀d [Intern(x, g) ∧ Owns(g, d) ∧ Sensitive(d) → ¬Authorized(x, d)]
Uploading a dataset to a public repository is considered publishing the dataset. ∀x ∀d [UploadedToPublicRepo(x, d) → Publishes(x, d)]
Anyone who publishes a sensitive dataset without authorization violates the research data policy. ∀x ∀d [Publishes(x, d) ∧ Sensitive(d) ∧ ¬Authorized(x, d) → ViolatesPolicy(x)]

1.2Prolog clauses

A Prolog rule (a Horn clause) cannot have a negative conclusion, so we cannot write ¬Authorized(x, d) as the head of a rule. Instead, we add an ordinary predicate, not_authorized(X, D), which means “X is not authorized to publish D”.

Notably, we did not write \+ authorized(X, D) (negation as failure), because \+ only means “this cannot be found in the knowledge base”. We have no authorized facts, so the check would pass for everyone and the intern rule would never be used. A professor who uploaded a sensitive dataset would also count as violating the policy, even though the statements only say that interns are not authorized.

Figure 1 shows the clauses.

1.3Proof that anna violates the research data policy

The query violates_policy(anna) matches the head of the violates_policy rule, which leaves three subgoals:

  1. publishes(anna, D): the publishing rule and the upload fact give D = medset.
  2. sensitive(medset): the sensitivity rule and the facts dataset(medset) and contains_patient_data(medset) prove it.
  3. not_authorized(anna, medset): the intern rule needs three more things. intern(anna, G) gives G = visionlab, owns(visionlab, medset) is a fact, and sensitive(medset) is proved again, as in step 2.

All three subgoals are proved, so violates_policy(anna) is true. Figure 2 shows the trace.

2Software Dependency Reasoning (Exercise 2)

2.1Knowledge base and recursive rule

Figure 3 shows the facts and the rule. The first clause is the base case (a direct dependency). The second clause is the recursive case: X depends on some Z, and Z requires Y.

Pressing ; returns every package that visionapp requires:

?- requires(visionapp, P).
P = pytorch ;
P = opencv ;
P = cuda ;
P = driver ;
P = numpy ;
false.

So visionapp requires pytorch, opencv, cuda, driver and numpy.

Figure 4 shows the trace for requires(visionapp, driver). The package driver is not a direct dependency of visionapp, so the first clause fails and Prolog backtracks into the recursive clause. That clause follows visionapp → pytorch, where the direct check fails again, and then pytorch → cuda, where depends_on(cuda, driver) succeeds. This proves the chain visionapp → pytorch → cuda → driver. The answer true . means a choice point was still open (for example the opencv branch), and we pressed <enter> instead of asking for more proofs.

2.2Clause order and cyclic dependencies

Both versions are in one file under different names, requires_a (Version A) and requires_b (Version B), so they run on the same facts (Figure 5).

2.2.1Effect of clause order

Clause order changes the proof search because Prolog tries a predicate’s clauses from top to bottom. It searches depth-first: it goes as deep as it can along one path, and backs up to try another when that path fails. Figure 6 shows both traces side by side.

  • Version A first checks whether driver is a direct dependency, and only goes one level deeper if it is not. It checks visionapp (no), pytorch (no), then cuda (yes). The proof takes 18 steps and never looks at driver’s own dependencies.
  • Version B goes deeper first, following visionapp → pytorch → cuda → driver. The package driver has no dependencies, so both clauses of requires_b(driver, driver) fail. Prolog backs up to requires_b(cuda, driver) and tries its second clause, which succeeds. This dead end (depth 15–16 in the trace) is why the proof takes 22 steps.

Both versions mean the same in logic, so they prove the same facts. Only the order of the proof steps changes, so the order of the answers changes too: Version A returns the direct dependencies first, and Version B returns the deepest first (Figure 7).

2.2.2Effect of a cyclic dependency

Adding the fact depends_on(driver, pytorch) creates a cycle: pytorch → cuda → driver → pytorch. The problem is that a query may never finish (non-termination). Prolog does not remember which goals it is already trying to prove, so it can go round this cycle forever. The results below are with the cycle fact uncommented.

Version A. requires_a(visionapp, driver) still gives its first answer, because the first clause finds driver at cuda, before the search gets back to pytorch. Asking for more answers goes round the cycle forever: the same answers repeat, and numpy is never reached. However, a query that should be false, such as requires_a(cuda, opencv), never finishes and gives no error, so we stopped it with a time limit (Figure 8).

Version B. Even the true query requires_b(visionapp, driver) gets no answer. The recursive clause is always tried first, so Prolog keeps following cuda → driver → pytorch → cuda → … and never tries the second clause. Each round leaves that untried clause waiting, so the stack keeps growing until SWI-Prolog raises a stack-overflow error. With the default 1 GB limit it was still running after 5 minutes, so we used --stack-limit=64m, which fails in seconds (Figure 9).

The cause is the cycle together with Prolog’s depth-first search, which does not check for loops. Changing the clause order only decides whether an answer happens to be found before the search starts looping. Neither order removes the loop.
