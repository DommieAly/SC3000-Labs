Exercise 1: Research Data Sharing

1.1 First-Order Logic

StatementFOL
A research group called visionlab owns a dataset called medset. ResearchGroup(visionlab) ∧ Dataset(medset) ∧ Owns(visionlab, medset)
The dataset contains patient data. ContainsPatientData(medset)
anna is an intern at visionlab. Intern(anna, visionlab)
anna uploaded medset to a public repository. UploadedToPublicRepo(anna, medset)
Any dataset containing patient data is considered sensitive. ∀d [Dataset(d) ∧ ContainsPatientData(d) → Sensitive(d)]
An intern is not authorized to publish sensitive datasets owned by their research group. ∀x ∀g ∀d [Intern(x, g) ∧ Owns(g, d) ∧ Sensitive(d) → ¬Authorized(x, d)]
Uploading a dataset to a public repository is considered publishing the dataset. ∀x ∀d [UploadedToPublicRepo(x, d) → Publishes(x, d)]
Anyone who publishes a sensitive dataset without authorization violates the research data policy. ∀x ∀d [Publishes(x, d) ∧ Sensitive(d) ∧ ¬Authorized(x, d) → ViolatesPolicy(x)]

Intern(x, g) reads “x is an intern at research group g”, and Authorized(x, d) reads “x is authorized to publish d”.

1.2 Prolog clauses (team_qn_1_2.pl)

A Horn clause cannot have a negated head, so ¬Authorized(x, d) becomes the positive predicate not_authorized(X, D). We did not use negation as failure (\+ authorized(X, D)), because then the conclusion would rest on a missing fact rather than on the stated intern rule.

1.3 Proof that anna violates the research data policy

Prolog proves the query by refutation. It adds the negated goal ¬ViolatesPolicy(anna) and resolves it against the clauses until it reaches the empty clause. The goal unifies with the head of the violates_policy rule, which gives three subgoals:

  1. publishes(anna, D) resolves with the publishing rule and then the upload fact, binding D = medset.
  2. sensitive(medset) resolves with the sensitivity rule, then the facts dataset(medset) and contains_patient_data(medset).
  3. not_authorized(anna, medset) resolves with the intern rule: intern(anna, G) binds G = visionlab, then owns(visionlab, medset) and sensitive(medset) are proved again.

Every subgoal is resolved, so the empty clause is derived and violates_policy(anna) is true.

driver is not a direct dependency of visionapp, so the first clause fails and Prolog backtracks into the recursive clause. 2.2 Effect of clause order (team_qn_2_2.pl)

Both versions sit in one file under different names, requires_a (Version A) and requires_b (Version B), so they can be compared on the same facts.

{{PL:team_qn_2_2.pl}}

{{TRACE:q2_2_trace_a.txt}}

Version B (recursive clause first):

{{TRACE:q2_2_trace_b.txt}}

Prolog tries the clauses of a predicate from top to bottom and the subgoals of a body from left to right. It searches depth-first and backtracks on failure. The clause order therefore decides which branch of the search tree is explored first:

  • Version A first asks “is Y a direct dependency of X?” at each package, and only goes one level deeper if that fails. The trace checks visionapp (no), then pytorch (no), then cuda (yes). It finds the proof in 18 steps and never visits driver’s own dependencies.
  • Version B descends first. It follows the first dependency at each level all the way to the bottom (visionapp → pytorch → cuda → driver) before trying any base clause. At driver both clauses of requires_b(driver, driver) fail, because driver has no dependencies. Prolog then backtracks to requires_b(cuda, driver) and tries its second (base) clause, which succeeds. That detour (the extra Call/Fail/Redo at depth 15–16) makes the proof 22 steps.

Both versions have the same declarative meaning, so they prove the same facts. Only the procedural proof sequence changes. The order of the answers changes too: Version A returns shallow dependencies first, and Version B returns the deepest first.

{{TRACE:q2_2_all_ab.txt}}

Adding depends_on(driver, pytorch).

This fact closes a cycle: pytorch → cuda → driver → pytorch. The problem is non-termination (infinite recursion). The recursive clause calls itself on pytorch, cuda, driver, pytorch, … forever. Prolog’s depth-first search does not remember which goals it is already trying to prove (there is no loop check), so the search tree now contains an infinite branch. Results with the cycle fact uncommented:

Version A. The first answer to requires_a(visionapp, driver) is still found, because the base clause hits driver before the cycle is entered. Backtracking, however, goes round the cycle forever. Asking for all packages gives an endless stream of duplicates, and numpy is never reached because the pytorch branch never finishes. A query that should be false, such as requires_a(cuda, opencv), never terminates. Here the recursive call is the last, deterministic call, so SWI-Prolog’s last-call optimisation runs the loop in constant memory. It spins forever without any error, so we stopped it with a time limit:

{{TRACE:q2_2_cycle_a.txt}}

Version B. Even the true query requires_b(visionapp, driver) gets no answer. Because the recursive clause is always tried first, Prolog keeps following cuda → driver → pytorch → cuda → … and never backtracks to a base clause. The trace repeats the same three calls at ever greater depth. Each level leaves a choice point for the untried base clause, so the stack grows until SWI-Prolog raises a stack-overflow error. With the default 1 GB limit it was still running after 5 minutes, so we ran it with --stack-limit=64m, where it fails in seconds.

{{TRACE:q2_2_cycle_b.txt}}

The cause is the cycle in the data combined with Prolog’s depth-first, loop-unaware proof procedure. Reordering the clauses only changes whether an answer happens to be found before the infinite branch is entered. Neither order makes the search terminate. A terminating version would have to remember visited packages (for example, pass a visited list and check \+ member(Z, Visited)), or use SWI-Prolog tabling (:- table requires/2.).
